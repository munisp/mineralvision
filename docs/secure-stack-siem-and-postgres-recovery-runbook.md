# Secure Stack Integration Testing, SIEM Shipping, and PostgreSQL Recovery Runbook

**Author:** Manus AI  
**Scope:** The MineralVision secure Docker Compose reference stack, including Caddy, APISIX, OpenAppSec, Keycloak, OPA, FastAPI, PostgreSQL, and Redis.

> **Operating boundary:** The default task sandbox is not a production host and should not be used as a durable SIEM, backup repository, or database recovery environment. Run this procedure on a controlled persistent host or managed platform with private networking, off-host backups, monitored storage, and an approved incident process.

## 1. Preflight and Change Controls

Before starting the stack, obtain approved values from the organization secret manager for every `REPLACE_WITH_*` entry in `security/.env.security.example`. Use immutable image digests after vulnerability review, restrict the backup object store and SIEM collector to private connectivity, and ensure that all participating hosts use synchronized UTC time. The restore target must use the **same PostgreSQL major version** as the backed-up cluster.

Use a dedicated staging environment for the initial deployment. It requires two DNS names—one for the application and one for Keycloak—and a real Keycloak realm/client configuration. Do not test production blocking, quotas, MFA, or point-in-time recovery for the first time during an incident.

```bash
export RUNTIME_ENV=/secure/runtime/mineralvision.env
# The file is generated by a secret manager; do not create it in the repository.

# Validate the combined configuration before starting containers.
docker compose --env-file "$RUNTIME_ENV" \
  -f docker-compose.secure.yml \
  -f docker-compose.observability.yml \
  config --quiet

# Verify committed static security, observability, and PITR contracts.
python3 scripts/verify_security_baseline.py
python3 scripts/verify_operations_baseline.py
```

The observability overlay must be included whenever the organization requires log forwarding. It places the Fluent Bit Forward listener on `127.0.0.1:24224`, not on a public interface.

## 2. Start and Validate the Secure Compose Stack

Start the stack only after the compose configuration and secret substitution checks pass.

```bash
docker compose --env-file "$RUNTIME_ENV" \
  -f docker-compose.secure.yml \
  -f docker-compose.observability.yml \
  up -d

docker compose --env-file "$RUNTIME_ENV" \
  -f docker-compose.secure.yml \
  -f docker-compose.observability.yml \
  ps
```

Verify that Caddy is the only service with public `80` and `443` mappings. APISIX, PostgreSQL, Redis, OPA, Keycloak administration, the API, and Fluent Bit must not be Internet-reachable. Inspect Caddy’s response protections from an authorized test client:

```bash
curl --fail --silent --show-error --head "https://${PUBLIC_FQDN}/health" | \
  grep -Ei 'strict-transport-security|content-security-policy|x-content-type-options|x-frame-options'
```

The public API surface is intentionally authentication-protected. A request without a bearer token should be rejected by FastAPI after Caddy/APISIX route handling; it is not an authentication health check. Keycloak and the web client must complete Authorization Code + PKCE flow before API access is tested.

### End-to-End Oil-Spill Review Test

The repository provides `scripts/run_mfa_review_integration_test.py`. It does not generate or forge access tokens. Obtain three short-lived tokens from a **non-production** Keycloak realm:

| Environment variable | Required Keycloak state | Test role |
|---|---|---|
| `OPERATOR_TOKEN` | Valid OIDC token with `oil_spill_operator` | Creates a four-pixel, `test_only` annotation record. |
| `REVIEWER_NO_MFA_TOKEN` | Valid `oil_spill_reviewer` role with no recognized `amr`/`acr` MFA claim | Negative control; review must receive HTTP 403. |
| `REVIEWER_MFA_TOKEN` | Valid `oil_spill_reviewer` role with a verified WebAuthn/step-up assurance claim | Positive control; review must transition to `confirmed`. |

```bash
export MINERALVISION_API_URL="https://${PUBLIC_FQDN}"
export MFA_REVIEWER_ID="staging-reviewer"
# Supply tokens through secure short-lived shell/session injection, not history files.
export OPERATOR_TOKEN="..."
export REVIEWER_NO_MFA_TOKEN="..."
export REVIEWER_MFA_TOKEN="..."

python3 scripts/run_mfa_review_integration_test.py \
  --api-url "$MINERALVISION_API_URL" \
  --output artifacts/mfa-review-$(date -u +%Y%m%dT%H%M%SZ).json
```

A successful run proves the deployed path Caddy → APISIX → FastAPI OIDC validation → OPA → PostgreSQL review persistence for a controlled incident. It is not a penetration test, a capacity test, or proof of Keycloak security. The script intentionally retains the test incident as auditable evidence; remove it only through an approved retention process.

### Edge and WAF Test Gates

Perform non-destructive staging checks only. Test body-limit and quota behavior with synthetic files or approved imagery; do not submit malware, real victim data, or unapproved attack payloads.

```bash
# Confirm that only the exact image route accepts image analysis POSTs.
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --request POST "https://${PUBLIC_FQDN}/api/oil-spill/analyze/image"

# Confirm that Fluent Bit is healthy and that protected service logs are tagged.
docker compose --env-file "$RUNTIME_ENV" \
  -f docker-compose.secure.yml -f docker-compose.observability.yml \
  logs --tail=100 fluent-bit
```

For rate-limit validation, perform a small authorized burst below production-impacting thresholds in staging and confirm APISIX returns `429` after the configured quota. For WAF validation, start OpenAppSec in the release-supported detection/learning procedure, review events, then test prevention only after the security team approves the behavior.

## 3. External SIEM Log Shipping

`docker-compose.observability.yml` and `security/observability/fluent-bit.conf` implement a vendor-neutral log-shipping pattern. Docker forwards selected service stdout/stderr using the `fluentd` driver to a host-loopback Fluent Bit Forward input. Fluent Bit adds `platform=mineralvision` and `environment`, tails the OpenAppSec agent log volume for releases that write WAF events there, and forwards to an external collector using the Forward protocol with a shared key and verified TLS CA.

Set the following secret-managed variables:

```bash
FLUENT_BIT_IMAGE=cr.fluentbit.io/fluent/fluent-bit@sha256:<vetted_digest>
SIEM_FORWARD_HOST=<private-collector-name>
SIEM_FORWARD_PORT=24224
SIEM_FORWARD_SHARED_KEY=<random-high-entropy-shared-key>
SIEM_CA_CERT_PATH=/secure/certificates/siem-ca.pem
```

The external collector must expose a **private** Forward-compatible TLS endpoint, validate the presented stream, and route records by Docker tag. The expected tags are `mineralvision.caddy`, `mineralvision.apisix`, `mineralvision.appsec-agent`, `mineralvision.appsec-file`, `mineralvision.keycloak`, and `mineralvision.api`. The shared key is not a substitute for network policy or TLS certificate verification.

| Source | Implemented source channel | SIEM coverage and remaining action |
|---|---|---|
| Caddy | JSON stdout access/error events | Shipped by the Docker logging driver. Index HTTP status, host, method, latency, and request volume; do not ingest bearer tokens. |
| APISIX | Container stdout/stderr | Shipped by the Docker logging driver. Verify the selected APISIX/OpenAppSec attachment release emits access/rate-limit records to stdout; configure its vendor release accordingly if it does not. |
| OpenAppSec | Container stdout plus read-only `appsec-logs` volume tail | Shipped by both paths; deduplicate by event ID/timestamp at the collector. The committed WAF policy disables headers and request-body logging. |
| Keycloak | Container stdout/stderr | Shipped by the Docker logging driver. **Realm and administrative events require a configured Keycloak event listener/exporter**; the realm enables event generation but the repository does not ship a vendor-specific event-exporter plug-in. Deploy a reviewed listener and confirm login, role/group change, and admin events reach the SIEM. |
| MineralVision application audit | API stdout plus PostgreSQL tables | Stdout is shipped. `audit_logs` and `oil_spill_incident_events` are not automatically exported by Fluent Bit; use a read-only database exporter, audited CDC pipeline, or scheduled signed report to deliver them to the SIEM. |

### Log-Shipping Verification

1. Trigger one authorized staging login, one rejected MFA-less review, one allowed MFA review, one controlled APISIX rate-limit response, and one benign OpenAppSec detection test.
2. Query the SIEM by a bounded UTC interval and `platform=mineralvision`.
3. Verify an event from every listed tag and correlate the OIDC subject, Keycloak role change/login, edge request, OPA decision/application `403`, and review audit event without storing raw tokens or images.
4. Alert on forwarding backlog, Fluent Bit retry growth, collector TLS failures, missing Keycloak admin events, and a silent WAF stream. A healthy container does not prove that events reached the external collector.

## 4. PostgreSQL Backup, Disaster Recovery, and PITR

The committed `postgresql-pitr.conf` and `pgbackrest.conf.template` establish the configuration baseline for continuous WAL archiving and encrypted pgBackRest repository storage. They are **not yet mounted by `docker-compose.secure.yml`**, because the supplied PostGIS container image does not automatically contain pgBackRest or include the WAL fragment. Build and security-review a custom PostGIS/PostgreSQL image that installs the matching pgBackRest version, renders the protected template at runtime, and includes `postgresql-pitr.conf` in PostgreSQL configuration. Do not simply copy a config file into a running production data directory.

PostgreSQL PITR requires a usable base backup and an uninterrupted archived WAL sequence. `pg_dump` and `pg_dumpall` are logical backups and cannot supply WAL replay for PITR. PostgreSQL documents that archiving requires `wal_level=replica` or higher, `archive_mode=on`, and a working archive command or archive library. [1] pgBackRest provides full, differential, incremental backup, archive, encrypted repository, check, and restore controls used by the supplied template. [2]

### Initial Backup Configuration and Verification

1. Create an encrypted, versioned, access-controlled backup bucket or independent repository host. Enable separate administrator roles, deletion protection/object lock according to retention policy, private endpoints, and cross-region replication if required by the business recovery plan.
2. Store repository access credentials and `PGBACKREST_CIPHER_PASS` in a secret manager separate from the database and container secrets. Losing the cipher passphrase makes encrypted backups unrecoverable; storing it only beside the repository defeats encryption.
3. Render `security/postgres/pgbackrest.conf.template` into a root-owned, database-readable runtime configuration. Set `PGBACKREST_REPO1_S3_REGION` according to the selected S3-compatible store.
4. Include `security/postgres/postgresql-pitr.conf` in the server configuration, restart PostgreSQL, and confirm settings:

```sql
SHOW wal_level;
SHOW archive_mode;
SHOW archive_command;
SELECT archived_count, failed_count, last_archived_wal, last_failed_wal, last_failed_time
FROM pg_stat_archiver;
```

5. On the database host/container, initialize and test the pgBackRest stanza. Commands must run under the database operating-system user and exact, release-approved pgBackRest binary/configuration.

```bash
pgbackrest --stanza=mineralvision stanza-create
pgbackrest --stanza=mineralvision check
pgbackrest --stanza=mineralvision --type=full backup
pgbackrest --stanza=mineralvision info
```

`check` forces/validates an archived WAL segment; it must succeed before declaring PITR ready. Monitor archive failures continuously. PostgreSQL will retain unarchived WAL, potentially filling disk and causing an outage, if archiving fails repeatedly. [1]

### Example Backup Schedule

The template retains two full backups and seven differential backups. This is an example that must be sized to measured WAL volume, required retention, RPO, RTO, legal obligations, and recovery-test results. Run the schedules from a restricted scheduler identity or CI runner; do not place backup credentials in a general user crontab.

```cron
# Example only: UTC scheduler on the protected database/backup host.
15 02 * * 0 pgbackrest --stanza=mineralvision --type=full backup
15 02 * * 1-6 pgbackrest --stanza=mineralvision --type=diff backup
45 03 * * * pgbackrest --stanza=mineralvision expire
```

`archive_timeout='60s'` requests a WAL switch at least at that cadence during low activity, but it does **not** guarantee a 60-second RPO. Actual RPO includes archive command latency, repository availability, and monitoring/response time. Measure it from successfully archived WAL timestamps.

### Disaster Recovery and Point-in-Time Restore

Never perform a first restore directly into the only production data directory. First restore into an isolated recovery host or new encrypted volume with the same PostgreSQL major version, pgBackRest version/configuration, repository credentials, and cipher passphrase.

1. Declare the target in UTC and record the business reason, change approval, target timestamp, desired RPO/RTO, and incident evidence identifier. For accidental deletion, pick a point immediately before the confirmed bad transaction, not an approximate local-time value.
2. Freeze risky application writes. For a production replacement, stop API/Keycloak writers and preserve the original data volume rather than deleting it. For a forensic/table-level investigation, recover to an isolated cluster and extract only reviewed data.
3. Provision an empty recovery data directory. Ensure it is not owned by the active primary and that the repository is reachable read-only except where the backup tool requires otherwise.
4. Run a time-targeted restore with the approved pgBackRest binary. The exact target syntax and restore options must be tested for the selected version before incident use:

```bash
# Example: restore the full cluster to the last recoverable state before the target UTC time.
pgbackrest --stanza=mineralvision \
  --type=time \
  --target='2026-08-20 14:32:00+00' \
  --target-action=promote \
  restore
```

5. Start PostgreSQL in the isolated recovery environment and wait for WAL replay/promotion to finish. Verify the recovered timeline and application data before directing any client traffic:

```sql
SELECT pg_is_in_recovery();
SELECT now() AT TIME ZONE 'UTC' AS recovery_validation_time;
SELECT datname FROM pg_database ORDER BY datname;
SELECT count(*) FROM oil_spill_incidents;
SELECT count(*) FROM audit_logs;
```

6. Validate Keycloak database availability, API migrations, OPA policy bundle, sample OIDC login, MFA-negative/positive review test, and application health. Only after written approval should DNS/load balancer traffic move to the recovered service.
7. If replacing production, preserve the pre-recovery cluster and recovery logs for investigation. Rebuild backup/WAL archiving on the promoted cluster, create a fresh full backup, and run `pgbackrest check` before closing the incident.

### Recovery Testing and Evidence

Run a scheduled restore drill at least as often as the risk policy requires. Each drill should restore to an isolated environment, verify `pgbackrest info`, replay to a chosen point, validate both `mineralvision` and `keycloak` databases, run the MFA review integration test, measure elapsed recovery time, and record the result in the change/incident system. A successful backup job alone is not evidence that recovery will meet the RTO.
